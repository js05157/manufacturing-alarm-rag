# 검색·답변 검증 개선

## 변경 범위

기존 E5 임베딩과 ChromaDB 인덱스를 유지하고 검색 순위 결합과 근거 선택을 수정했다. PDF 재추출, 임베딩 모델 교체, 재색인은 수행하지 않았다. 신규 패키지 설치와 requirements.txt 변경은 없다.

| 구분 | 변경 내용 |
|---|---|
| 자연어 검색 | E5 거리 순위, BM25 본문 순위, BM25 제목 순위를 RRF로 결합했다. 한국어 2·3글자 묶음과 공백을 제거한 3글자 묶음을 사용한다. |
| 운전 조건 | 원문 제목에 명시된 가속·정속·감속/정지 구간을 대조한다. 과전류 차단과 차단을 방지하는 스톨 방지 표시는 구분한다. ‘운전 중 정지했다’는 결과를 정지 구간으로 해석하지 않는다. |
| 근거 범위 | 다른 알람을 함께 확장하던 처리를 선택된 알람 레코드로 제한했다. 원문에서 묶인 별칭과 E.SAF 사양별 레코드는 보존한다. |
| 모호한 질문 | 같은 명칭의 서로 다른 코드, 운전 구간이 빠진 보호 알람은 표시 코드나 구간을 확인한다. |
| 복수 확인 부위 | 원문 증상 표의 ‘확인 부위’와 질문을 대조한다. 부하와 입력 신호를 함께 요청하면 한 부위의 행만 상위를 차지하지 않도록 선별하고, 선택된 근거의 관련도 순서를 유지한다. |
| 코드 판별 | E.EHR 내부의 EHR을 별도 경고 코드로 잘못 인식하던 경계를 수정했다. |
| 로컬 생성 | Qwen3가 관련 근거 ID를 최대 2개 선택한다. 프로그램이 전체 원문을 복원하고 필수 점검·대처·주석과 출처를 원래 순서로 보완한다. |
| 대화 | 운전 구간 확인 질문 뒤 ‘감속 중이야’ 같은 응답으로 기존 증상을 다시 검색한다. 새 코드와 새 채팅방은 구분한다. |
| 저장 | Windows에서 기록 시각이 같을 때 메시지 일련번호로 최근 채팅 순서를 유지한다. 회귀 검사에서 발견한 정렬 오류를 수정했다. |

BM25는 Python 표준 라이브러리로 계산하며 저장된 원문을 메모리에서 읽는다. E5 검색을 생략하거나 모델을 대체하는 경로는 추가하지 않았다. RRF 상수는 60, BM25 계수는 k1=1.2, b=0.75다. 기존 E5 거리 제한 0.30과 상위 근거 3개 설정은 유지한다.

## 평가 방법

비교 기준은 개선 전 커밋 `97d7b26`이다. 같은 SQLite·Chroma·E5 모델에서 이전 검색 코드와 변경된 검색 코드를 각각 실행했다. 원본 40문항과 정답은 수정하지 않았다.

추가 25문항은 알람 코드가 정답인 자연어 질문 15개, 증상 표 질문 5개, 미등록·근거 부족 질문 5개로 구성했다. 질문을 작성한 뒤 비교 실행했지만 개발 중 결과를 확인했으므로 외부 독립 시험 세트로 분류하지 않는다. 추가 문항 명세 SHA-256은 `563287bb6d6a9ff0f8e54c07f6364f3777e7d2e0de2c82e79484b5052c9b66e2`다.

Hit@1·Hit@3는 정답 알람 코드가 있는 자연어 질문만 사용한다. 코드 중복을 제거한 순위로 계산하며 코드 직접 입력, 코드 없는 증상 표, 미등록 질문은 제외한다. 검색 후보에 코드가 포함되더라도 최종 응답이 확인 질문이면 답변 점수가 자동으로 올라가지 않는다.

답변 검사는 필수 원문 항목, 원문 순서, 코드와 PDF/문서 페이지를 대조한 프로그램 검사와 질문 적합성 검토를 구분한다. 실제 Qwen 응답은 모두 검토 대기 상태로 저장하며, 검토 승인과 답변 지문이 일치하고 프로그램 검사도 통과해야 정답으로 집계한다. 검토자는 Codex이며 설비 전문가의 독립 검수는 수행하지 않았다. 이 점수는 원문 근거를 제시하는 파이프라인의 문항 대응 결과이며 실제 고장 원인 진단 정확도가 아니다.

원문 검색 확인 모드의 `diagnostic_pass`는 개발 점검용이다. 실제 LLM 답변 점수에 섞지 않는다. 모의 HTTP/LLM을 쓰는 pytest와 실제 llama.cpp 추론도 따로 집계한다.

## 해석상 제한

- 원본 n07은 ‘부족 전압’만으로 E.UVT를 정답으로 지정했다. 매뉴얼에는 UV도 같은 명칭으로 존재한다. 질문에 표시 코드와 운전 조건이 없으므로 현재 응답은 코드 확인 요청이다. 기존 정답을 수정하지 않아 엄격한 답변 채점에서는 실패로 남는다.
- 추가 문항도 개발자가 작성하고 결과를 확인한 세트다. 새로운 현장 표현과 독립 평가 문항에 대한 일반화 성능은 미측정이다.
- 대화 맥락은 코드·증상과 최근 조건을 이어받는 규칙 기반 처리다. 모든 한국어 생략 표현과 긴 대화를 이해하는 대화 모델 평가는 아니다.
- 응답 시간은 이미 로드된 모델과 E5를 사용한다. 서버의 prompt/KV 캐시는 켜져 있고 답변 문자열 캐시는 없다. 모델 최초 로딩, 브라우저 렌더링, 다중 사용자 부하는 측정 범위 밖이다.
- 출력은 근거 선택과 원문 복원 방식이다. 자유로운 원인 추론, 확정 진단, 매뉴얼 밖 문서 조회 기능은 포함하지 않는다.
- 일부 응답에서 참고 자료 제목이나 덜 직접적인 항목을 강조 근거로 선택했다. 필수 점검·대처는 별도로 전부 복원되지만, 이 검사 통과를 강조 근거 선택의 최적성으로 해석하지 않는다.

## 원본 보존과 기록

기존 SQLite, Chroma manifest, 원본 평가 질문·정답·결과·보고서·문항 명세의 SHA-256이 모두 유지됐다. Chroma의 전체 문서·메타데이터·임베딩을 정렬한 지문도 변경되지 않았다. 컬렉션 `e800_eee4c84748796e8d`의 224개 청크를 재사용했다.

인덱스 지문은 `9caa34998d38154f7b93f090a77ae8a2140c3a16f14709436a9f8f11f20494ae`다. 원본 PDF, 모델 가중치, 인덱스, 대량 원문과 응답, .env는 커밋하지 않았다.

운영 앱의 최신 코드 적용은 Streamlit의 Clear caches와 재실행으로 수행했다. 프로세스 재시작 명령은 자동 승인 검토에서 차단돼 실행되지 않았다. 캐시 갱신 후 기존 대화 목록과 정상 화면을 확인했고, 앱과 모델의 상태 응답은 모두 HTTP 200이다. 앱과 llama.cpp 프로세스는 종료하지 않았다.

실행별 상세 결과와 실패 기록은 Git에서 제외한 `evaluation/local_llm/improved/`에 보존한다. `retrieval_v3`는 검색 비교, `full`·`full_v2`는 40문항 전후, `additional_llm`·`a18_patch`·`additional_final`은 추가 문항 전후 및 검토, `validation`·`validation_v2`는 대화·시간 측정을 담는다. `final_freeze.json`은 마지막 코드와 입력 지문 대조 및 원본 보존 결과다.
